# Security Policy

This document reflects **current main** behavior in code (see `api/src/server.ts`, `api/src/services/host-auth.ts`, `api/src/security/*`).

## Supported Versions

Security fixes land on `main`. Backports are not guaranteed—cherry-pick fixes to your deployment branch.

## Reporting a Vulnerability

Email the maintainers or open a private channel with ops. Include:
- Impact synopsis and affected surfaces.
- Repro steps or PoC.
- Logs/config that aid triage (redact secrets).

We acknowledge within 3 business days and share an assessment/fix ETA shortly after.

## Hardening Checklist (code-backed)

- **TLS/mTLS for admin**: `ADMIN_ACCESS_MODE` accepts `mtls`, `cookie` or `open` and defaults to `mtls`. The client-certificate requirement itself is enforced by the bundled Caddy config for `/admin*`; in the API the mode is only consulted on the CLI device-code route, where `ADMIN_ACCESS_MODE=open` drops the admin-session requirement. If you front admin without client certificates (`ADMIN_ACCESS_MODE=cookie`), put the admin surface behind VPN/firewall; admin login is enforced once at least one active admin user exists.
- **Admin sessions**: Admin login uses an HTTP-only session cookie (`ADMIN_SESSION_COOKIE`) with a configurable TTL (`ADMIN_SESSION_TTL_MINUTES`, default 43200). The issued session is clamped between 300 seconds and 7 days; the rolling refresh on each authenticated admin request clamps to 30 days. Treat admin cookies as sensitive and ensure TLS is enforced end-to-end.
- **Password recovery**: reset requests use a uniform response for known and unknown identifiers, store only a SHA-256 token hash, expire after one hour, and are single-use. A successful reset applies the password policy, expires the user's sessions and reset tokens, and removes their passkeys so the recovered password can be used.
- **API key binding**: Host API keys are IP-bound on first successful authenticated host request. Later calls from a different IP are 403 unless roaming is allowed, insecure-host IP override/grace applies, or runner CIDR bypass matches (`AUTH_RUNNER_IP_BYPASS` + `AUTH_RUNNER_BYPASS_SUBNETS`).
- **Reverse DNS checks**: When enabled, forward A/AAAA + PTR matching is enforced only on routes calling `authenticate(..., enforceReverseDns=true)` (`POST /auth`, `DELETE /auth`, `POST /sync/status`, `POST /sync/bootstrap`).
- **Encryption at rest**: Canonical auth bodies and per-target tokens are encrypted with libsodium `secretbox` (`sbox:v1:` legacy, `sbox:v1:kid=<id>:` rotation-aware) using `AUTH_ENCRYPTION_KEY` or keyring mode (`AUTH_ENCRYPTION_KEYS` + `AUTH_ENCRYPTION_ACTIVE_KID`). Host API keys are hashed (SHA-256) for lookup and also stored encrypted (`api_key_enc`).
- **Rate limits**: Global IP bucket (default 120 req / 60s, every request except OPTIONS and the bypass list) and a dedicated auth-failure bucket (default 20 fails / 10m) backed by `ip_rate_limits`.
- **Insecure host windows**: Hosts marked `secure=false` use a sliding window (`insecure_enabled_until`, 0–480 minutes, default stored window 10; initial provisioning window 30). Window enforcement currently applies to `/auth` retrieve-style calls and routes calling `enforceInsecureWindow` (`POST /mcp`, `GET/POST /host/lane`). `store` uploads are not blocked by this window gate in `handleAuth`; they still require normal auth/IP/reverse-DNS/runner checks. Admin disable operations clear both `insecure_enabled_until` and `insecure_grace_until`.
- **Insecure domain auto-allow**: Active `insecure_domain_allows` entries can auto-open insecure windows for matching subdomains.
- **TLS verification bypass is risky**: Per-host `curl_insecure` returns installer commands that use `curl -k`, makes installer-internal downloads reuse `curl -k` (the generated installer defaults `CODEX_INSTALL_CURL_INSECURE` to 1), and bakes `allow_insecure` into the host wrapper config so sync traffic skips TLS verification. This exposes installer/API keys/auth payloads to MITM; prefer trusting the correct CA whenever possible.
- **Installer tokens**: Single-use UUID tokens (`install_tokens` table) with a TTL fixed at 1800s in `api/src/services/host-management.ts` — there is no env knob for it. Creating a new token deletes any prior pending token for that host. Tokens are stored as SHA-256 hashes plus Secretbox-encrypted ciphertext (token + API key); DB access is still sensitive but plaintext is no longer present at rest.
- **Kill switch**: `api_disabled` flag (set via `/admin/api/state`) returns 503 for every route except exact path `/admin/api/state`.
- **Forwarded IP trust**: `X-Forwarded-For`/`X-Real-IP` are honored only when `TRUST_X_FORWARDED=1` and the socket peer address matches `TRUSTED_PROXY_CIDRS`; otherwise (including when `TRUSTED_PROXY_CIDRS` is empty) the socket peer address is authoritative.
- **MCP origin gate**: `GET/POST /mcp` reject any request carrying a non-empty `Origin` header with 403 unless `MCP_ALLOW_REQUEST_HOST_ORIGIN` (default off) is set. An absent/empty `Origin`, which is the normal case for non-browser MCP clients, is allowed.
- **MCP privilege boundary**: host-authenticated `POST /mcp` uses dedicated MCP credentials (`authenticateMcpCredential`) and exposes only the host-safe memory, shared-memory, resource, Skill, project, and fleet-secrets tools. Coordinator filesystem helpers (`fs_*`) are not available on that public route.
- **Agent Messaging is opt-in and fail-closed**: the fleet switch is seeded off, every host's switch defaults off, and runtime eligibility additionally requires an active secure host, the address's engine enabled on that host, and an enabled/unarchived address. Send, bind, claim, renew, and acknowledgement paths recheck these gates in their mutation transactions. Host deletion, insecure/status transitions, engine removal, and fleet/host/address disable atomically cancel queued/leased work, mark already accepted work ambiguous, revoke applicable relays, and generation-fence bindings rather than leaving replayable work behind.

## Data Handling

- **Auth payloads**: Stored in `auth_payloads.body` encrypted; native-target tokens in `auth_entries.token` encrypted. Digests are SHA-256 of the canonical JSON. Every host, admin, seed, and bootstrap candidate must pass the engine's live runner before it can advance `auth_canonical_heads`; pending/failed generations remain encrypted quarantine and are never returned to hosts, admin body reads, or compatible gateways. Canonical payloads are also validated on read (timestamp bounds, digest match, native credential projection, token quality, and keyed credential-pair fingerprint where present).
- **Token quality checks**: Tokens must meet entropy/length rules (`TOKEN_MIN_LENGTH` min 8, default 24), no whitespace, not placeholder strings, and must contain enough unique characters.
- **API keys**: Lookups use SHA-256 hashes; encrypted copy kept for dashboard displays/downloads. Do not expose `api_key_enc`/`api_key_hash` outside trusted operators.
- **Secrets**: `.env` and DB data/volumes contain encryption key material, API key ciphertexts/hashes, and encrypted auth/token snapshots. Installer and wrapper downloads also contain plaintext API keys for the target host; treat those responses/logging paths as sensitive.
- **Fleet secrets store** (`secrets`): the working credentials agents use once running — GitHub PATs, database passwords, service tokens, SSH keys. Separate from engine-boot auth above by lifecycle and blast radius, and never promoted into `auth_canonical_heads`. `value_enc` is the only copy of a value and always holds an `sbox:v1:` envelope; there is no plaintext column and deliberately no `value_sha256`, because a digest of a human-chosen password is offline-crackable and would hand a database-dump attacker what the envelope exists to deny them. Every metadata read enumerates its columns so ciphertext cannot ride along, and the admin DTO is typed on a shape with no ciphertext field. Delivery to hosts is MCP-only; the orchestrator does not automatically write plaintext to a host filesystem. A task can nevertheless create a requested copy after `secret_get`, and revocation only prevents future reads rather than removing that copy. Reads are gated by `secrets_module_enabled`; mutations and the plaintext reveal require the owner or admin role, and the reveal is a `POST` so it cannot be prefetched, cached by an intermediary, or replayed from browser history. `secret_get` writes its own `mcp_access_logs` row carrying the slug before returning a value and does not swallow a failed write, so an unaudited credential read cannot occur.
  - **Where the boundary is.** `secret_get` puts plaintext into the requesting agent's context window — that is the delivery model, not a defect. The protection boundary is the database and the wire: encryption at rest, role-gated authoring, and an audited read path. The guidance prefers a tool-native secret parameter, then stdin, an inherited descriptor, or a process-scoped environment variable, but permits persistence or relay when the task explicitly requests it. Shell tracing remains disabled, diagnostic output is sanitized, and temporary variables are cleaned up. Treat any secret an agent has read as disclosed to that agent's transcript, and scope what you store accordingly.
  - **No verification analogue.** Unlike `auth_payloads`, nothing here is runner-verified: there is no runner that can prove a database password still works. `last_rotated_at` (advanced only when an update genuinely changes the value) and the admin surface are the whole freshness story.
- **Agent Messaging content**: `agent_bus_messages.content_enc` and `last_error_enc` are secretbox envelopes; admin list routes enumerate metadata and never decrypt them. Plaintext exists on the scoped participant delivery/read paths and on the explicit owner/admin `POST /admin/agent-messaging/messages/{id}/reveal` path. Reveal writes an admin audit event, never broadcasts the plaintext or a reveal event over WebSocket, and returns `Cache-Control: no-store` plus `Pragma: no-cache`. The admin UI retains at most one closeable reveal and clears it when role, filters, or result data changes. Version 1 retains terminal bus rows and their audit history indefinitely unless an operator introduces a later retention mechanism; no automatic history purge exists today.

## Authentication & Authorization

- **Host-authenticated routes**: `POST/DELETE /auth`, `POST /sync/status`, `POST /sync/bootstrap`, `/wrapper*`, `/host/users`, `/host/lane`, `/agents/retrieve`, `/config/retrieve`, `/skills*`, `/mcp/memories/*`, `POST /mcp`, `GET /host/agent-portal/state`, and `POST /host/agent-sessions` require API key authentication and IP binding (subject to roaming/insecure overrides/runner CIDR bypass rules). After registration, each agent session gets a short-lived, session-scoped bridge bearer. The wrapper keeps that bearer out of the engine child environment and command line by proxying a fixed operation allowlist over a private Unix socket. The engine's normal provider/proxy credentials remain governed by their existing launch paths.
- **Agent portal boundary**: The permanent URL places its reusable bearer in the URL fragment, so it is not sent in the initial HTTP request. The SPA exchanges it once for a Secure, HttpOnly, SameSite=Strict cookie and immediately removes the fragment from browser history. Every `/go/api/*` request must be same-origin; mutations require the exact configured public origin, and browser fetch metadata is rejected when it reports cross-site. Reusable link tokens and browser-session tokens are looked up only by SHA-256 hashes; the reusable token is also Secretbox-encrypted solely so an owner/admin can read the same link back for re-bookmarking, through one gated, audited endpoint that is not the user listing. Portal messages, safe timeline payloads, and prompts are Secretbox-encrypted at rest. SSE re-authenticates while holding the same global/user/session locks used by revocation, so a disable or logout cannot race a later event read. The portal has no outbound push channel at all: it replaced one that mailed a rendered deep link with every lifecycle event, so live bearer material no longer leaves the box on a schedule, and a leaked link is contained by rotation instead of having been broadcast N times already.
- **Agent portal authority**: Portal text enters the active root agent as ordinary user text through the scoped `cxx portal` relay. It cannot approve a tool action, answer an execution-time approval prompt, grant credentials, widen scope, or write to a PTY directly. Only bounded user-facing status and answer text is publishable; hidden reasoning and raw tool output are excluded. Bridge requests revalidate the active host, engine, host-key fingerprint, rolling bridge expiry, session, and global switch inside the mutation transaction. The wrapper socket is mode `0600` inside a mode `0700` directory, which prevents cross-user access but is not a sandbox from other same-UID processes. Queue delivery is ordered and at-least-once: `wait` only leases, stable claim UUIDs recover lost responses, and `accept` acknowledges after delivery to the model in the same transaction as its visible event. The global switch defaults off on first deployment; disabling it or an individual user revokes browser sessions and cancels queued/leased undelivered work without replay. Finished sessions are read-only and purged after the configured 24-hour retention window; live sessions whose bridge heartbeat expires are failed and retained read-only instead of remaining writable indefinitely.
- **Agent Messaging authority and delivery boundary**: the engine gets neither a host API key nor a relay bearer. `cxx` retains the short-lived session bridge credential and exposes only the fixed Agent Messaging operations over its private Unix socket. The background relay is outbound-only, authenticates once with the host key, then uses a hashed, 15-minute, generation-fenced token; it opens no listener and skips addresses with an attached interactive session. Stable addresses do not confer authority by themselves: every operation revalidates session/address binding and the complete fleet/host/security/engine/address gate. The bus supports all Codex/Claude direction pairs and treats peer text as ordinary model input, not approval or authorization. Delivery is ordered at least once, per-target FIFO, and one-in-flight; attempts are capped at 12. `accepted` is the non-replay boundary: a lost completion acknowledgement, shutdown after acceptance, or accepted lease expiry becomes terminal `ambiguous`. Only an owner/admin can create an explicit linked redrive.
- **Agent Messaging admin roles**: any authenticated active admin role may inspect fleet state, stable addresses, conversations, and message metadata. Alias changes, fleet/host/address switches, conversation cancellation, redrive, and plaintext reveal require `owner` or `admin`; host deletion and security/engine transitions share that gate because they revoke bus work. Viewers never receive message content from list endpoints.
- **Admin routes** (`/admin/*`): mTLS gate by default. Admins can view verified canonical auth, submit runner-gated auth candidates, and rotate keys—restrict to trusted operators only.
- **Installer** (`/install/{token}`): public endpoint that returns a shell script; token is validated for expiry/one-time use and tags host/base URL plus installer mode. Returned script bakes API key/FQDN/base URL into the engine-appropriate wrapper(s).
- **Installation binding**: If a client sends `installation_id` and it does not match server `INSTALLATION_ID`, auth calls are rejected with `403 installation_mismatch`. Omitted `installation_id` is accepted for legacy clients.
- **Runner**: External validator invoked by the background auth-verification worker and by store/admin triggers (`AUTH_RUNNER_URL`). Existing verified auth remains readable when it is unavailable, but every canonical-changing store requires a configured, reachable runner and a positive live verdict. Runner requests can be authenticated with `AUTH_RUNNER_SHARED_SECRET`/`RUNNER_SHARED_SECRET` (`X-Runner-Auth` header).

## Abuse Controls

- **Global rate limit**: Configured via `RATE_LIMIT_GLOBAL_PER_MINUTE` and `RATE_LIMIT_GLOBAL_WINDOW` (defaults 120 req/60s). It runs on every non-OPTIONS request, including `/admin/*` and `/go/api/*`; only `/healthz`, `/admin/ws`, `/admin/_app/`, `/admin/manual/articles/`, `/admin/favicon` and immutable `/go/assets/` are skipped.
- **Auth-fail rate limit**: `RATE_LIMIT_AUTH_FAIL_COUNT`/`RATE_LIMIT_AUTH_FAIL_WINDOW` (defaults 20 fails/600s) guard repeated missing/invalid API keys and respond 429 with `bucket` + `reset_at`. There is no separate block window: the counter window itself is what has to elapse.
- **Pruning**: Hosts are pruned/logged as `host.pruned` when inactive past `inactivity_window_days` (default 30, max 60, 0 disables inactivity pruning), never provisioned for 30 minutes, or expired via `expires_at`. Temporary host `expires_at` is refreshed by successful authenticated contact (+2h).

## Logging & PII

- Logs (`logs` table) capture action metadata (including digests/IP fields where provided). Token usage lines are sanitized to strip ANSI/control characters and capped to 1000 chars.
- Full auth/API tokens are not intentionally logged in normal flows, but install/seed log entries include a short redacted token prefix (first 8 chars + ellipsis).
- Admin endpoints can return the verified canonical auth body when explicitly requested; avoid enabling this unless necessary and ensure transport security.

## Backup & Recovery

- Back up the MySQL database **and** `.env` (contains `AUTH_ENCRYPTION_KEY` or `AUTH_ENCRYPTION_KEYS`). Without key material, encrypted auth payloads, API keys, Agent Messaging bodies/errors, and other secretbox data cannot be decrypted.
- Wrapper signing key (stored in the `wrapper_signing_keys` table and loaded by `api/src/services/wrapper-signing-key.ts`) must be included in your backup set. Losing it means every host has to be re-keyed (operator provisions a new key, rebuilds the Go binaries with the new public key embedded, and the hosts self-update). Wrapper binaries under `storage/wrapper/v2/bin/` can be reproduced from a `wrappers/` checkout and CI tag.

## Operational Notes

- In production (`APP_ENV=production`), set `PUBLIC_BASE_URL` and keep `PUBLIC_BASE_URL_REQUIRED=1` so startup/health fails fast on misconfiguration.
- When using forward proxies/CDN, set `TRUST_X_FORWARDED=1`, scope `TRUSTED_PROXY_CIDRS` tightly, and strip inbound forwarded headers from untrusted clients.
- Runner IP bypass (`AUTH_RUNNER_IP_BYPASS`, `AUTH_RUNNER_BYPASS_SUBNETS`) should be scoped tightly and defaults to off in `.env.example`.
