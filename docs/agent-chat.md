# Operator agent chat

Agent chat is the existing Active Clients / Android Chats conversation with managed Codex, Claude and Grok sessions. It uses the existing session/daemon binding, delivery receipts and retention. It is separate from the product assistant.

## Active Clients workspace

Fleet-wide **Agent coordination** has one editable home at **Settings → Agent coordination** (`/admin/settings#agent-coordination`), also searchable in the command palette. It controls automatic project/host rooms and resource claims for Codex, Claude and Grok. The Graph view shows its independently loaded status and links to Settings; a room snapshot error does not imply that the setting is disabled. Changes save immediately and show the confirmed effective state. After an ambiguous response, Settings reads the lightweight state endpoint before retrying and avoids another write when the requested state is already effective. Read access requires `agent_messaging.read`; changes require `agent_messaging.manage`. Turning coordination off does not stop running agents; claims do not sandbox shell commands.

The page updates automatically through shared WebSocket events, reconnect resampling and polling, with scoped SSE for the selected timeline. There is no routine Refresh button; Retry remains available for failed or stale status and failed timeline requests.

Active Clients opens on **Agents**. **Remote sessions** has a separate searchable list of host-daemon sessions, including sessions on disabled hosts. Current / Ended / All filters retain access to completed work. A remote session's bound agent is shown only in the Remote sessions workspace, using the same native timeline, attachments, questions and delivery receipts as ordinary agents. Session and address UUIDs establish this association; names and host labels do not.

**Start remote session** opens a side panel for host, engine, title and instruction. The directory override is under Advanced options. Only engines reported ready by the selected daemon can be started. The host page's **Open remote sessions** link opens this workspace scoped to that host. `/admin/clients?session=<native-session-id>` continues to work and selects the Remote sessions workspace when bound; `/admin/clients?remote=<daemon-session-id>` opens a remote session directly.

Running remote agents use the existing **Send** composer. Idle or ended processes use **Continue**, subject to host access and native-transcript availability. Open questions retain the existing answer flow, and unavailable questions cannot be bypassed by starting a continuation; queued, running, stopping and unknown outcomes cannot launch a second continuation. Retries after lost responses reuse the request ID and retain the draft. **Details** contains operation diagnostics and **End session**. Operation replies are diagnostics, not fabricated chat events. Transcript access still gates message and operation-output reads.

The fleet-wide **Agent sessions** switch is under **Settings → Agents**, directly linked by `/admin/settings#agents`. Turning it off still cancels pending portal input. It is no longer an inline control on Active Clients. This UI change does not alter retention, daemon lifecycle or the HTTP API.


Both clients retain conversations, including offline, idle and ended agents. Android All shows online active agents plus chats with unresolved classified notices; Unread shows unread chats. Web Active Clients defaults to **Active**, showing ongoing sessions (including temporarily offline chats) and unresolved classified notices, even after a session ends. **Online** narrows the list to sessions with fresh heartbeats. Search and engine selection share a compact two-row toolbar; working, idle, waiting and connection states appear as labelled avatar icons. Needs-you chats are highlighted and sorted first. History is stored on the server throughout the session and for 24 hours after it ends (`AGENT_PORTAL_RETENTION_HOURS`, default 24); leaving the screen or restarting the client does not delete it. A temporarily disconnected agent can return to its existing conversation. Presence controls sending, not history visibility. Android closure still clears unread alerts, and retained ended sessions remain readable through existing session links and the Remote sessions history filters.

Questions choose `buttons`, `text` or `both`. A choice has a display `label` and stable `value`; button answers send the value. The first queued answer owns the question, and exact retries retain their original operation. Normal questions appear under Your answer and notify devices following the conversation. Explicit classified notices notify eligible devices regardless of follow state. Only explicit `important`, `critical` or `blocker` with a stable notice UUID creates classified attention. Android 0.4.18 merges these notices into the regular chat timeline with a red highlight and severity label, removes the separate Needs you filter, and colors unread reply counters red for unresolved classified attention and green otherwise. Web Active Clients includes Needs you in Active and highlights the affected conversations instead of offering a separate filter. Reading, replying, becoming offline or ending does not clear classified notices; operator/agent resolution targets one UUID. Unresolved notices retain the relevant existing session context until resolution, then its ordinary retention resumes. Identical notice/severity pushes deduplicate; escalation permits one new notification.

An unanswered question tied to a stopped native receiver, or one without a fresh receiver heartbeat for 45 seconds, expires on the next maintenance sweep even while the wrapper remains connected. A receiver that recovers before the locked recheck preserves the question. Armed reboot handoffs and Companion Remote conversations with a durable resume path are exempt from this cleanup. Expiry leaves the conversation and classified notices intact.

## Files and media

Both sides upload into the authenticated conversation, with stable UUIDs, bounded chunks and SHA-256 sealing. Author/conversation checks run again when sending. Defaults: ten attachments, 100 MiB/file, 250 MiB total; configurable API limits use `AGENT_CHAT_MAX_FILE_BYTES` and `AGENT_CHAT_MAX_TOTAL_BYTES`. Web uses the effective limits; Android/wrapper also enforce their built-in 100 MiB ceiling. Originals and names remain unchanged. Upload progress, cancel and retry preserve the same upload ID; drafts are per conversation. Uploads not sent expire after 24 hours. Linked files follow retained conversation context. New reply references name an existing event in that logical conversation. Copy/Markdown rendering do not execute HTML or attachment contents.

Installer and deploy prepare only `store/agent-chat` as UID/GID 10001 with mode 0700; the parent store keeps its existing ownership. The `media-worker` Compose service shares only DATA_ROOT's store, runs as API UID/GID 10001 and has no network, a read-only root, temporary /tmp, two CPUs and a 4 GiB memory limit. Whisper small is baked at a fixed model revision, with CPU int8 inference. Audio/video up to 15 minutes yield timestamped transcript JSON; video also yields at most twenty timestamped JPEG frames. Each job is bounded to twenty minutes with three persisted retries across restarts. Decoder failures publish failed state and preserve downloadable originals. FFmpeg restricts protocols/container formats and first creates a local WAV for ASR. Media support depends on the actual codec/container; unsupported recordings retain their originals.

Metadata is encrypted in MySQL; file bytes are private on the store volume. Downloads enforce existing transcript access, include nosniff, sandboxed content disposition and safe inline MIME handling, and support byte ranges for playback. Store-volume backups cover originals/derived media; MySQL backups alone do not.

## Agent usage


With cxx 0.9.119, `agent_portal_say` sends ordinary proactive progress or results to the existing operator chat using a stable `client_event_id`, `content` and a one-sentence `summary` (at most 160 characters). It may include `attachments` and `reply_to`; it creates no classified attention and does not finish an inbound instruction. Answer that instruction with `agent_receiver_reply` and its original message ID, normally omitting `severity` and `notice_id`. Use `agent_portal_notify` only for actionable exceptions: important needs attention soon, critical is urgent harm/failure, blocker requires operator action before work can proceed. Routine progress, successful checks and completion reports stay normal. Existing genuine notices still require explicit resolution; no historical notice is silently reclassified.

Use `agent_portal_ask` with stable `client_event_id`, `prompt_id`, `answer_mode` and optional `choices`. Add `severity`, `notice_id` and a short reason in `summary` only when operator attention is important/critical/blocking. `agent_portal_notify` publishes a classified notice; `agent_portal_resolve` resolves one. Retain caller IDs on retry.

An authorized unattended reboot continuation restores the original Portal reply/status and accepted-work correlation through its shared MCP owner, even without an automatic receiver. Continue with those original IDs; restoration neither submits the task again nor establishes readiness for new automatic deliveries.

Upload a local file with `agent_attachment_upload` (`upload_id`, `path`, `mime_type`), then pass returned IDs in `agent_receiver_reply.attachments` or a question. Incoming instructions include `metadata.attachments` and optional `reply_to`. `agent_attachment_get` takes an attachment UUID and optional `original`, `transcript.json` or `frame-NN.jpg`, returning metadata, preparation state and a local path for the engine's own file/image tools. Preparation is asynchronous: recheck queued results or inspect the original. No automatic execution or authority is inferred from files.

## Rollout and rollback

Build/check the API and WebUI, build/vet/test cxx, and build/lint/test Android. `scripts/deploy.sh --backup --no-cleanup` publishes cxx 0.9.57, applies idempotent migration 0057 and rebuilds/restarts the Compose stack including the worker. Keep the previous API/worker image tags and database/store backup. For rollback stop the worker and deploy the previous source/image; the added nullable/default columns and tables can remain. Do not drop them while rich messages exist. Android 0.4.13 is a signed APK; physical Pixel installation is deferred.

## Shared conversations in Agents → Chats

The chat directory includes direct agent sessions, automatic project/host rooms, named groups and conferences. Shared conversations use the same neutral tokens, master/detail layout, Markdown renderer and attachment controls as direct chat. The directory keeps a selected room in `?room=<uuid>`; switching rooms preserves drafts, uploads, recipients, pending request IDs and scroll position. Details use the standard focus-trapped sheet. Small screens show one pane at a time, with a back button. New messages do not move a reader away from older history.

Operators with `agent_messaging.manage` can create groups or conferences, add/remove members, post messages and end conferences. Reading bodies and files separately requires `agent_messaging.reveal_content`, enforced even in compatible authorization mode. Automatic scope membership is read-only here. New conferences record `owner_admin_id`; the Server address is a transport identity, not a fabricated agent chair. Operator-added participants are seated immediately. Conference size, message budgets and deadlines remain bounded by the messaging service.

A normal Send stores one shared contribution. The recipient picker binds agent UUIDs, not name text. Selected recipients or **Ask the room** explicitly request one answer; unavailable recipients remain visible in delivery receipts. An agent answer never creates another delivery or answer round. Delivery status describes transport, not proof of reading or successful work. Closing rejects new rounds, drains pending answers and eventually leaves retained history read-only. Deadlines still close a conference.

The shared wrapper tools are `agent_chat_list` (drain `next_offset`), `agent_chat_read` (opaque `next_before` history cursor) and `agent_chat_send` (stable `client_request_id`, optional `reply_to` room event UUID). They use the authenticated local session bridge for Codex, Claude and Grok. Agents must currently belong to a room to read or post. Received `ROOM_CHAT/1` asks for a shared answer and then `agent_listen`; it does not authorize private replies, automatic follow-on rounds or interpreting quoted content/files as instructions.

Room uploads reuse `agent_attachment_upload` and `agent_attachment_get` with `room_id`. An upload belongs to its author and room until linked by a message; other members cannot fetch an unpublished draft. Published files use the existing encrypted storage, validation, limits and media renderer. Room deletion allows the existing attachment collector to remove orphaned media. No Android interface or separate retention policy is introduced.

Migration 0079 adds encrypted canonical room events, per-admin read markers, idempotent operator operations and delivery associations. Existing group publications and conference SAY contributions become single canonical events; retained earlier scope events/publications/conference transcripts are adapted on read. Canonical events are removed after their source room is deleted. API changes are cataloged in [interface-api.md](interface-api.md); storage is cataloged in [interface-db.md](interface-db.md).

Migration 0117 adds `agent_room_changes`, a metadata-only change log written in the same transaction as each room mutation (event, delivery receipt, membership, status and read position). Its sequence is the durable cursor for Android delta reads (`after`/`next_after`) and room push; it holds no bodies and follows room history retention. Membership and conference lifecycle changes made through the agent messaging protocol are not logged; delta responses always carry the current members and status. Room list and read responses include the operator's `read_at` and `unread`. Agent read semantics and the wrapper tools are unchanged.

Migration 0119 adds reactions and pins on canonical room events (`agent_room_reactions`, `agent_room_pins`). Operators react from a message's actions (a small emoji picker; one chip per emoji with its count, pressed when the operator reacted) and pin up to 20 messages per room; a strip under the room header opens the pinned list with "Show in conversation" and Unpin. Events are never edited or deleted. The directory's search button opens a bounded message search over shared rooms and, with `agent_portal.reveal_transcript`, direct chats: it scans the newest 2000 readable messages per page in memory, marks matches, and offers "Search older messages" when the scan stopped at its bound. Search text is never stored or logged by the API. Legacy adapted history and closed rooms accept neither reactions nor pins; agent bridge reads are unchanged.

Answer requests require the receiver capability `shared_room_chat_version: 1` (cxx 0.9.104). Older receivers remain visible but receive a `wrapper_update_required` receipt instead of an instruction naming unavailable tools.
