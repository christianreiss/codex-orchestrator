## Measurement

The baseline is a 120.432-second delta of MySQL 8.4 Performance Schema statement
digests, from 07:52:44 to 07:54:45 UTC. Observer queries are excluded. CPU is the
container cgroup CPU-time delta divided by elapsed wall time, expressed as a
percentage of one core. HTTP counts are incoming requests, not WebSocket frames
or application events. No general query log was enabled and no statistics were
reset. Statement digests contain placeholders, not credential values.

This is an active fleet sample, not a controlled no-client benchmark: five fresh
native sessions and 19 live relay rows were observed before it. The investigation
and an advisor contributed requests. Container restarts were zero and no warning
or error was observed in the baseline window.

All queue acceptance, result, cancellation, lease, canonical-auth generation,
account assignment and operator-audit writes carry durable state. They must
commit before success is acknowledged. They are not suitable for a lossy buffer.
The measured INSERT count is small; repeatedly checking for absent work and
persisting liveness dominate this sample.

## Cache, buffer and communicator boundaries

The first changes deliberately remove unnecessary work without increasing the
set of cached authorization tables or extending durable liveness lag. A larger
liveness buffer requires **all** presence consumers, including SQL sweeps,
recovery, operator snapshots and multi-process readers, to agree on a fenced
RAM overlay. Extending the current ten-second flush alone would produce false
offline sessions and unsafe recovery. Multi-row heartbeat UPDATEs also have a
documented deadlock history with transactions that lock several sessions.

Communicators can carry one persistent subscription per host/user, combine
native clients' polls, and forward invalidation/deadline hints. They should not
decide canonical account admission, lease ownership, or execution acceptance.
Any new subscription protocol needs capability negotiation, a reconnect cursor,
generation fencing, no lost-wake window, and legacy-client fallback. The existing
content RAM cache already saves byte transfer/rendering but still performs fresh
server confirmations; moving bytes alone does not remove those SQL reads.

Zero queries in some idle seconds is a valid target. A sustained zero SQL rate
with the current persisted liveness deadlines, active sessions, scheduled work
and independent quota writer is not the current contract. It requires replacing
polling with change/deadline scheduling and a coherent liveness design, not merely
increasing TTLs. Production measurements after rollout must be reported before
claiming that the idle CPU/SQL target has been reached.
