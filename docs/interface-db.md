# Database Interface (Source of Truth)

Schema DDL is defined in the Drizzle schema at `api/src/db/schema.ts` (MySQL only). Column names and types below are derived from that schema file.

Operationally, schema changes live as reviewable hand-written SQL in `api/src/db/migrations/` and are applied by the migration runner in `api/src/db/migrator.ts`. It runs automatically at API boot (`RUN_MIGRATIONS_ON_BOOT`, default **on**) and explicitly from `scripts/deploy.sh` between `compose build` and `compose up`; `node dist/migrate.js` (`npm run migrate` in a checkout) drives it by hand, with `--check`, `--list`, `--dry-run`, `--baseline`, and `--reapply`. Applied versions are recorded in `schema_migrations` with the file's sha256, and a `GET_LOCK` advisory lock serialises concurrent runners. Boot fails closed when a migration is pending and `RUN_MIGRATIONS_ON_BOOT` is off. Migrations must be idempotent — `test/integration/db-migrations/migrator.test.ts` re-applies every file against a migrated schema to prove it. See `api/src/db/README.md` for the full contract. **Do not use `pnpm drizzle:push`**: it ignores the migrations folder and reconciles the *entire* hand-maintained `schema.ts` mirror against the live DB, so any pre-existing drift is applied alongside the intended change. It also cannot express FULLTEXT indexes or foreign keys, so it would propose dropping `idx_memories_search`, `idx_coord_project_memories_search`, `idx_shared_memories_search`, and `idx_shared_memory_chunks_search`, and would create the `shared_memory_*` children without their `ON DELETE CASCADE` constraints. `0006_add_shared_memories.sql` back-fills both the indexes and the FKs for exactly that case, but the general warning stands.

Codex fields remain on the base names; Claude keeps parallel host-level fields so one host can track both engines without collapsing them into one record.
- **hosts.browseros_mcp_enabled** — `TINYINT(1) NOT NULL DEFAULT 0`; per-host Codex-only BrowserOS MCP toggle. When enabled, host config baking injects `[mcp_servers.browseros]` pointing to `http://127.0.0.1:9000/mcp` and bumps `hosts.config_version`.
- **auth_payloads** — canonical auth generation history (`id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, engine/timestamp/digest/encrypted body/source fields, plus `generation`, `source_kind`, `parent_payload_id`, `credential_kind`, keyed-HMAC fingerprint metadata, native issue/expiry metadata, `superseded_at`, and `purge_after`). The current distributable row is selected through `auth_canonical_heads`; `generation` is unique per engine. `body` remains libsodium `secretbox` ciphertext. Credential fingerprints use the encryption keyring only as HMAC key material and never contain plaintext tokens. Runner readbacks with `pending` or `failed` verification may be retained as quarantined history, but never become the head. Current canonical rows have no retention deadline; a row receives `superseded_at` and `purge_after` only when replaced by a verified successor.
- **auth_canonical_heads** — one explicit verified canonical pointer per engine (`engine` primary key, `payload_id` unique, `generation`, `updated_at`). Only a candidate that completed positive live runner verification may advance it. Migration `0005_add_auth_generation_ledger.sql` adds the ledger columns/indexes and this table. Boot backfill decrypts existing rows, derives keyed fingerprints/freshness, assigns per-engine generations, marks only historical rows superseded, and records marker `auth_generation_ledger_v1`.
- **auth_payloads canonical resolution** — `last_refresh` remains a VARCHAR for
  compatibility, but the service parses RFC3339 values and orders them by the
  represented instant, then by descending `id` on a tie only as a legacy
  fallback when no explicit head exists. Before a row can be
  selected, the decrypted body must be JSON, its body/row timestamps must name
  the same instant, its SHA-256 must match, its engine must be known, it must
  be within the accepted timestamp window (2000-01-01 through server now plus
  300 seconds), and it must contain a quality-checked credential for the
  engine's native target (`api.openai.com` or `api.anthropic.com`). With no
  explicit head, legacy fallback considers only structurally valid `verified`
  rows. With an explicit head, that exact generation remains authoritative:
  if later verification marks it failed, its bytes are withheld and resolution
  does not resurrect an older verified row. Quarantined `pending`/`failed`
  descendants are available only to verification and administrative
  inspection. Codex bodies are normalized to one native mode
  (`auth_mode=chatgpt` plus `tokens`, or `auth_mode=apikey` plus top-level
  `OPENAI_API_KEY`) before live verification. Legacy/non-native or
  partial/stale-fingerprint rows are not distributable; the worker verifies the
  exact current projection and advances the head only with a freshly
  fingerprinted verified replacement. Canonical bodies and `auth_entries`
  retain only the selected engine-native target; arbitrary extra targets are
  stripped before runner verification and persistence.
- **auth_entries** — the selected engine-native token mirrored for each payload (`id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, `payload_id` BIGINT UNSIGNED NOT NULL FK → `auth_payloads.id`, `target` VARCHAR(255) NOT NULL, `token` TEXT NOT NULL, `token_type` VARCHAR(32) DEFAULT `bearer`, `organization` VARCHAR(255) NULL, `project` VARCHAR(255) NULL, `api_base` VARCHAR(255) NULL, `meta` JSON NULL, `created_at` VARCHAR(100) NOT NULL); index: `idx_entries_payload` on (`payload_id`); unique key `uniq_entry_target` on (`payload_id`, `target`). - **coord_project_memories** — durable project-scoped memories (`id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, `project_id` BIGINT UNSIGNED NOT NULL FK → `coord_projects.id`, `memory_key` VARCHAR(128) NOT NULL, `content` LONGTEXT NOT NULL, `metadata` JSON NULL, `tags` JSON NULL, `tags_text` TEXT NULL, `source_host_id` BIGINT UNSIGNED NULL FK → `hosts.id`, `created_at` VARCHAR(100) NOT NULL, `updated_at` VARCHAR(100) NOT NULL); unique key `uniq_coord_project_memory_key` on (`project_id`, `memory_key`); indexes: `idx_coord_project_memories_project` on (`project_id`), `idx_coord_project_memories_updated_at` on (`updated_at`), fulltext `idx_coord_project_memories_search` on (`content`, `tags_text`). Unlike `mcp_memories` these are project-scoped, so they are visible from every host; `source_host_id` records which host wrote each row. Rows hard-delete (no `deleted_at`) — `coord_project_events` is the audit trail. The fulltext index is created by `api/src/db/migrations/0003_add_coord_project_memories.sql`, which is the DDL source of truth for this table: Drizzle's mysql-core cannot express FULLTEXT, so `schema.ts` omits it and `searchMemories` degrades to a LIKE scan when it is absent. That migration is idempotent and re-runnable, and also back-fills the index onto a table that already exists without it — which is precisely what `drizzle:push` creates, since it builds the table from the `schema.ts` mirror. No key prefix is reserved — the `^coco` reservation on `mcp_memories` exists to redirect callers *here*. Key uniqueness is case-insensitive (`utf8mb4_unicode_ci`) while the app treats keys as case-sensitive strings; lookup and constraint agree, so behaviour is consistent, but `Deploy` and `deploy` are the same row. Same latent quirk as `mcp_memories`.

- **mcp_memories** — MCP memory store scoped per host (`id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, `host_id` BIGINT UNSIGNED NOT NULL FK → `hosts.id`, `memory_key` VARCHAR(128) NOT NULL, `content` LONGTEXT NOT NULL, `metadata` JSON NULL, `tags` JSON NULL, `tags_text` TEXT NULL, `summary` TEXT NULL, `created_at` VARCHAR(100) NOT NULL, `updated_at` VARCHAR(100) NOT NULL, `deleted_at` VARCHAR(100) NULL); unique key `uniq_memories_host_key` on (`host_id`, `memory_key`); indexes: `idx_memories_host` on (`host_id`), fulltext `idx_memories_search` on (`content`, `tags_text`). `summary` stores the short runner-generated description used by the managed AGENTS `## Memories` inventory when available. These rows are intentionally host-scoped. Keys matching `^coco(?:$|[._:-])` are reserved and rejected so CoCo shared handoffs cannot be mis-modeled here; the redirect target is `coord_project_memories` for project-scoped coordination state and `shared_memories` for fleet-wide reference documents.
- **shared_memories** — fleet-wide shared memory documents, scoped to neither host nor project (`id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, `slug` VARCHAR(160) NOT NULL, `title` VARCHAR(255) NOT NULL, `summary` TEXT NULL, `content` LONGTEXT NOT NULL, `content_sha256` CHAR(64) NOT NULL, `content_length` INT UNSIGNED NOT NULL DEFAULT `0`, `chunk_count` INT UNSIGNED NOT NULL DEFAULT `0`, `revision` INT UNSIGNED NOT NULL DEFAULT `1`, `metadata` JSON NULL, `tags` JSON NULL, `tags_text` TEXT NULL, `source_host_id` BIGINT UNSIGNED NULL FK → `hosts.id`, `source_engine` VARCHAR(16) NULL, `created_at` VARCHAR(100) NOT NULL, `updated_at` VARCHAR(100) NOT NULL, `deleted_at` VARCHAR(100) NULL); unique key `uniq_shared_memories_slug` on (`slug`); indexes: `idx_shared_memories_updated_at` on (`updated_at`), `idx_shared_memories_deleted_at` on (`deleted_at`), fulltext `idx_shared_memories_search` on (`title`, `summary`, `tags_text`). Documents run to 1 MiB, two orders of magnitude above the 32k cap on the other two memory stores, so relevance search runs over `shared_memory_chunks` rather than this table. `source_host_id` / `source_engine` are provenance only — reads are never filtered by them, which is the whole point of the table. No `^coco` reservation applies here. Host writes soft-delete (`deleted_at`, slug stays reserved); the admin delete is hard so the slug can be reused. The collation is `utf8mb4_unicode_ci`, so the unique key is case-insensitive; the service lower-cases every slug on write so lookup and constraint agree.
- **shared_memory_chunks** — retrieval units for `shared_memories` (`id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, `memory_id` BIGINT UNSIGNED NOT NULL FK → `shared_memories.id` ON DELETE CASCADE, `revision` INT UNSIGNED NOT NULL, `ordinal` INT UNSIGNED NOT NULL, `heading` VARCHAR(255) NULL (markdown heading breadcrumb), `content` TEXT NOT NULL, `char_start` INT UNSIGNED NOT NULL, `char_end` INT UNSIGNED NOT NULL, `tags_text` TEXT NULL, `created_at` VARCHAR(100) NOT NULL); unique key `uniq_shared_memory_chunk` on (`memory_id`, `revision`, `ordinal`); indexes: `idx_shared_memory_chunks_memory` on (`memory_id`, `revision`), fulltext `idx_shared_memory_chunks_search` on (`content`, `heading`, `tags_text`). The chunks of one revision tile their document exactly — chunk 0 starts at offset 0, each `char_end` is the next `char_start`, and the last ends at `content_length` — so a chunk range is also a character range. `revision` is denormalized from the parent because a rewrite inserts the new chunks before flipping the parent, and every read joins on `chunk.revision = memory.revision`; that makes a crash mid-rewrite leave orphan rows rather than a half-updated document, without wrapping a 500-row rewrite in a transaction.
- **shared_memory_revisions** — metadata-only audit trail for `shared_memories` (`id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, `memory_id` BIGINT UNSIGNED NOT NULL FK → `shared_memories.id` ON DELETE CASCADE, `revision` INT UNSIGNED NOT NULL, `op` VARCHAR(16) NOT NULL (`create`/`replace`/`append`/`delete`), `content_sha256` CHAR(64) NOT NULL, `content_length` INT UNSIGNED NOT NULL DEFAULT `0`, `delta_length` INT NOT NULL DEFAULT `0`, `source_host_id` BIGINT UNSIGNED NULL FK → `hosts.id`, `source_engine` VARCHAR(16) NULL, `note` VARCHAR(255) NULL, `created_at` VARCHAR(100) NOT NULL); unique key `uniq_shared_memory_revision` on (`memory_id`, `revision`); indexes: `idx_shared_memory_revisions_memory` on (`memory_id`). Bodies are deliberately not copied here — at 1 MiB per document a full-body history would dwarf the corpus it describes. This is attribution, not rollback. The FULLTEXT indexes and the cascade FKs for all three tables are created by `api/src/db/migrations/0006_add_shared_memories.sql`, which is the DDL source of truth: Drizzle's mysql-core can express neither, so `schema.ts` omits both and `shared_memory_search` degrades to a bounded substring scan (`degraded: true`) when the chunk index is absent.

Encryption: `AUTH_ENCRYPTION_KEY` (single-key mode) is generated into `.env` on first boot if missing. Optional keyring mode uses `AUTH_ENCRYPTION_KEYS` (`kid:base64,...`) plus `AUTH_ENCRYPTION_ACTIVE_KID` (see `api/src/security/keyring.ts`); new writes then include `kid` in the ciphertext prefix while legacy `sbox:v1:{base64}` remains decryptable. `api_key_enc`, `auth_payloads.body`, `auth_entries.token`, `install_tokens.token_enc`, `install_tokens.api_key_enc`, and `auth_seed_tokens.token_enc` are stored as secretbox ciphertexts via `api/src/security/secret-box.ts`. One-time backfills are gated by `versions` keys: `auth_secretbox_migration_v1` (`auth_payloads.body`, `auth_entries.token`, `install_tokens.token_enc`/`api_key_enc`) and `hosts_api_key_encryption_backfill_v1` (`hosts.api_key`/`api_key_hash`/`api_key_enc`).
